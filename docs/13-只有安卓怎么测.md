# 13 · 只有安卓手机，怎么把「双端」测出来

**这份文档解决一个很具体的问题：**

> 招聘要求"Android / iOS 原生技术、双端 demo"，
> 可我手上只有一台安卓手机，没有 Mac、没有 iPhone。
> 我该怎么证明这个项目真的是双端？怎么测？面试官问起来我怎么说？

**答案：你不需要 Mac，也不需要 iPhone。** 下面是一条从头到尾的顺序，
每一步都写清楚"做什么、看到什么算成功、失败了怎么办"。

**预计耗时：一个下午。**

---

## 0. 先理解：面试官到底要什么

招聘原文要的是**两样东西**，不是一台苹果设备：

| 他要的 | 你能给的 | 怎么给 |
|---|---|---|
| 项目链接 | GitHub 仓库地址 | [11 上传到 GitHub](11-上传到GitHub.md) |
| 应用功能录屏 | 一段手机操作视频 | 安卓真机录，[05 §二](05-录屏与打包.md) |

**注意："双端原生"看的是代码和产物，不是看你有没有那台设备。**

`app/android/` 和 `app/ios/` 两个目录都在这个仓库里，是货真价实的原生工程；
编译出来一个是 APK、一个是 `.app`。**这就是双端的证据。**

> 打个比方：你不需要拥有一台印刷机，才能证明你写的小说能印刷。
> 你只要有排版好的稿子（代码），再找一个印刷厂（GitHub 的免费 macOS 机器）印一本出来（构建产物 + 录屏）。

所以你要做的，是**用安卓做主力验证，用云端 Mac 补上 iOS 那一环**。下面开始。

---

## 1. 你手上需要有什么

| 东西 | 必须有吗 | 说明 |
|---|---|---|
| 一台安卓手机 | ✅ 必须 | 安卓 7.0 以上都行，能开 USB 调试 |
| 一根数据线 | ✅ 必须 | 要能传数据，**纯充电线不行**（很常见的坑） |
| Windows 电脑 | ✅ 必须 | 你已经有了 |
| 和电脑同一个 WiFi | ✅ 必须 | 手机要连电脑上的后端，靠的就是局域网 |
| GitHub 账号 | ✅ 必须 | 用来拿 iOS 的构建证据，免费 |
| Mac / iPhone | ❌ 不需要 | CI 会替你做 |
| Android Studio | ⚠️ 建议装 | 主要是为了它附带的 Android SDK；见 [01](01-环境搭建.md) |

## 2. 第一步：把后端开起来，并记住那个局域网 IP

**这一步不做，后面全是白费**——手机上会一直显示"连不上"。

打开一个终端（CMD 或 PowerShell）：

```bash
cd C:\Users\chenj\eclipse-workspace\demo0\backend
npm start
```

启动后会打印这样一个地址表（这是我在这台机器上真跑出来的输出）：

```
  MoneyNote API 已启动
  数据库文件   C:\Users\chenj\eclipse-workspace\demo0\backend\data\moneynote.db
  本机访问     http://localhost:3000
  安卓模拟器   http://10.0.2.2:3000
  局域网真机   http://192.168.1.7:3000     ← 要的是这一行！
```

**把「局域网真机」那一行里的 IP（例子里的 `192.168.1.7`）抄下来**，
你的肯定不一样（`192.168.0.x`、`172.x.x.x` 都可能）。

> ⚠️ **如果「局域网真机」打印了好几行**（装了虚拟机、WSL、Docker 就会有），
> 说明你的电脑有多个网卡。**只有你手机连的那个 WiFi 对应的那一个才对。**
> 不确定是哪个？逐个在**浏览器**里试 `http://那个IP:3000/api/health`，
> 打得开的就是。（下一节就是干这个的。）
>
> 我实测这台机器就打印了两行：`26.113.101.79` 和 `172.19.11.101`——
> 两个都不是家里 WiFi 的地址。**照抄文档里的 `192.168.1.7` 必然连不上**，
> 所以一定要用你自己终端里打印出来的数字。

> **为什么要记这个？** 手机和电脑是两台机器。
> 你在手机上说"localhost"，手机理解成**它自己**，那上面当然没有后端。
> 必须明确告诉它"后端在我电脑那个 IP 上"，这个 IP 就是电脑在局域网里的门牌号。

**先别关这个终端**，它要一直开着。后面手机上每点一下，你都能在这里看到一行日志——
这是很重要的验证手段，第 4 步会讲。

### 验证一下这个地址通不通（强烈建议）

在电脑浏览器里打开：

```
http://192.168.1.7:3000/api/health
```

看到 `{"ok":true,...}` 就对了。

**如果打不开**：后端没起来，或者 IP 抄错了。**先解决这个再往下**，
不然你在手机上排查半天，其实问题出在电脑这头。

## 3. 第二步：让手机认可这台电脑

### 3.1 打开开发者选项

1. 手机：**设置 → 关于手机**
2. 找到「版本号」（有的机型在「软件信息」里）
3. **连续点 7 次**，会提示"你现在处于开发者模式"
4. 返回设置，找到新出现的「开发者选项」
5. 打开 **USB 调试**

> 找不到「版本号」？不同品牌位置不一样，直接搜"<你的手机型号> 开发者选项 怎么开"。
> 华为/小米/OPPO/vivo 都有各自的叫法，这是手机厂商的差异，不是你操作错了。

### 3.2 连电脑并授权

1. 数据线插上电脑
2. 手机上会弹一个框：「**允许 USB 调试吗？**」→ 点**允许**
3. 勾选"一律允许"省得下次再问

> **没弹框？** 把线拔了重插；换一根线（**充电线真的不行**）；
> 或者下拉通知栏，把 USB 模式从"仅充电"改成"传输文件"。

### 3.3 确认 Flutter 看得见手机

```bash
cd C:\Users\chenj\eclipse-workspace\demo0\app
flutter devices
```

应该能看到一行带 `android-arm64` 的设备，后面写着你的手机型号。

**看到了** → 继续第 4 步。
**没看到** → 回 [09 排错速查](09-排错速查.md)，搜"flutter devices 看不到手机"。

## 4. 第三步：把 App 装到手机上（关键的一步）

在**刚才那个 app 目录**里跑：

```bash
flutter run --dart-define=API_BASE_URL=http://192.168.1.7:3000
```

> ⚠️ **把 `192.168.1.7` 换成你第 2 步抄下来的那个 IP。**
> 直接用上面这行、IP 却忘了改，是这一步最常见的失败原因。

第一次编译要 **3～10 分钟**（正在下载 Gradle 依赖），屏幕上滚一大片字是正常的，**别关**。

最后停在一句 `Flutter run key commands.` 并出现 `r`、`R`、`q` 提示，
说明 App 已经装到手机上并跑起来了。

### 看到什么算成功

手机上应该出现首页，顶部卡片有「2026年10月结余 ¥X,XXX.XX」这样的数字，
下面是一行行的流水记录。

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 手机上白屏 | 正在编译，再等等 | 等 30 秒 |
| 显示「连不上 http://…」 | 地址不对 / 不同 WiFi / 防火墙 | 见下面 4.1 |
| 显示「连不上 …」但地址看着没错 | Windows 防火墙拦了 3000 端口 | 见下面 4.1 |
| 手机上根本没有这个 App | 编译失败 | 看终端里红色的报错，贴给 AI |

### 4.1 连不上排查（按这个顺序，别跳）

1. **手机和电脑是同一个 WiFi 吗？** 手机连的是不是流量、或者访客网络？
   —— 这是第一大原因。
2. **手机浏览器打开 `http://192.168.1.7:3000/api/health`。**
   - 打不开 → 是**网络问题**，不是 App 问题。回到第 2 步。
   - 打得开 → 网络没问题，是你 `--dart-define` 里的地址敲错了。
3. **Windows 防火墙**：第一次跑 `npm start` 时如果弹过"是否允许 Node.js 访问网络"，
   你点了"取消"，就会被拦。去
   「Windows 安全中心 → 防火墙和网络保护 → 允许应用通过防火墙」，
   把 Node.js 的**专用网络**和**公用网络**都勾上。

> 这一步排查的价值，远不止于把 App 跑起来。
> 面试时被问"你怎么定位问题"，这套"先分清是网络问题还是代码问题"的思路
> 就是标准的答案——**先缩小范围，再动手改。**

## 5. 第四步：在安卓上把功能全点一遍（并留下证据）

现在 App 在手机上了，逐个功能点。**完整清单在 [10 §3](10-测试指南.md)**，
共 19 条，每条都有"期望结果"和打勾的地方。

但这里要教你一个**只有真机才能做、而且最能证明问题**的动作：

### 5.1 一边点手机，一边看电脑上的后端日志

把后端那个终端窗口和手机并排放着。**在手机上做任何操作时，
盯着后端终端——每次操作都应该多出一行。**

后端每处理一个请求就会打一行，长这样（格式是
`[状态码] 方法 路径 (耗时) 时间`）：

```
[200] GET /api/health (3.5ms) 12:59:54
[200] GET /api/stats?month=2026-10 (1.1ms) 12:59:54
[201] POST /api/records (11.6ms) 12:59:54
[204] DELETE /api/records/27 (1.0ms) 13:01:31
[404] GET /api/nope (0.5ms) 12:59:54
```

对照表：

| 你在手机上做的事 | 后端终端应该多出一行 |
|---|---|
| 打开 App | `[200] GET /api/stats?month=2026-10 …` 和 `[200] GET /api/records?month=… …` |
| 保存一笔新记录 | `[201] POST /api/records …` |
| 改一笔记录 | `[200] PUT /api/records/27 …` |
| 删一笔记录 | `[204] DELETE /api/records/27 …` |
| 点「上个月」箭头 | `[200] GET /api/stats?month=2026-09 …` |

**状态码怎么看**：看到 `[2xx]` 就是成功；`[4xx]` 是你发的数据有问题（比如金额填了 0）；
`[5xx]` 是服务器自己炸了——这种才需要去查代码。

**为什么这一步值钱？** 因为它把"看起来能用"变成了"确实打通了"。

> 界面上的数字**有可能**是本地缓存的旧数据。
> 只有后端日志里出现对应的那一行，才能证明**这次操作真的走到服务器又回来了**。
>
> 面试时如果被问"你怎么确认前后端真的联通了"，你就可以答：
> "我一边操作一边对照后端访问日志，每个动作都对应到一个具体的请求和状态码。"
> —— 这句话比"能用啊"有说服力得多。

### 5.2 再做一个"故意搞破坏"的动作

把后端终端 **Ctrl+C 停掉**，然后在手机上点「统计」。

**期望**：顶部数字变成 `—`（破折号），并出现一条错误提示，
**而不是显示 `¥0.00`**。

> 这一条是刻意设计过的。很多 App 在拿不到数据时会显示 0，
> 用户以为自己这个月没花钱——**这是比崩溃更糟的错，因为它安静地骗人**。
>
> 能做到"没数据就说没数据"，是一个能讲很久的加分点。
> 另外 5 个破坏实验见 [10 §4](10-测试指南.md)。

验证完把后端重新 `npm start` 起回来。

## 6. 第五步：测 release 包（**别跳过，这是最容易翻车的地方**）

上面跑的是**调试版**。给面试官装的、发到应用商店的，是 **release 版**——
而这两者**区别很大**，调试版能跑**不代表** release 能跑。

最典型的：Flutter 模板的网络权限**只加在了 debug 配置里**，
release 包会**完全没有网络权限**，装上去就是一个永远连不上后端的空壳。
（这个坑本项目已经修好了，见 [03 §4.1](03-跑通App.md)，但你要亲手验证一次。）

### 6.1 打包

```bash
cd C:\Users\chenj\eclipse-workspace\demo0\app
flutter build apk --release --split-per-abi
```

第一次要几分钟。成功后产物在：

```
app\build\app\outputs\flutter-apk\app-arm64-v8a-release.apk
```

> 现代安卓手机基本都是 `arm64`，装这个就行。

### 6.2 卸载旧的、装新的

**先卸载**手机上那个调试版（图标一样，不卸载会冲突）：

```bash
adb uninstall com.moneynote.money_note
```

> 这个包名来自 `app/android/app/build.gradle.kts` 里的 `applicationId`。
> 你要是改了项目名，包名也会跟着变——不确定就 `adb shell pm list packages | grep note` 查一下。

然后装 release 包：

```bash
adb install -r app\build\app\outputs\flutter-apk\app-arm64-v8a-release.apk
```

### 6.3 关键：release 包怎么连后端？

**不用改代码。** `--dart-define` 在 `flutter build` 的时候一样能用，
把它加到打包命令后面就行：

```bash
flutter build apk --release --split-per-abi --dart-define=API_BASE_URL=http://192.168.1.7:3000
```

（`192.168.1.7` 还是换成你第 2 步抄下来的那个 IP。）

> **为什么强烈建议用 `--dart-define`、而不是去改 `app_config.dart` 里的默认值？**
>
> 因为改了源码就会留下痕迹：你会把一个**只有你家 WiFi 能用的 IP**
> 提交到 GitHub 上。面试官克隆下来一跑，连不上，还以为你的项目是坏的。
> 用 `--dart-define` 的话，源码一个字节都不用动，打包时临时注入即可。

**这样打出来的包，只有在和你同一个 WiFi 下才能拉到数据。** 自己验证足够了。
但要**发给面试官**的话，他连不上你家 WiFi —— 那就得先把后端部署到公网
（[06](06-部署后端到公网.md)），拿到 `https://xxx.onrender.com`，再打一次：

```bash
flutter build apk --release --split-per-abi --dart-define=API_BASE_URL=https://xxx.onrender.com
```

**要发给别人的包，必须用这一个版本。** 这是整个流程里唯一一个
"你本机测着好好的、别人装上去就是坏的"的分界点。

> **这一步和"电脑关机了还能用"是同一件事。**
> 指向你家局域网 IP 的包，你电脑一关就是块砖；
> 指向 `https://xxx.onrender.com` 的包，**电脑关了、人在外面用流量，照样能用**——
> 因为数据是从别人家那台 7×24 开着的服务器上拿的。
> 完整做法（含"关电脑实测"的验收步骤）见 [06 部署后端到公网](06-部署后端到公网.md)。
>
> 顺带一提：那个后端已经配好了**空库自动补演示数据**，
> 所以你不用担心服务器重启后 App 打开是空的。

### 6.4 打开 release 版，再点一遍

**能拉到数据 = 通过。** 如果 release 版连不上、而调试版好好的，
那基本就是权限或地址的问题，回 [09 排错速查](09-排错速查.md)。

> 做完这一步你就有了一个可以讲的故事：
> "我给 release 包单独验证过一遍，因为调试版和正式版的权限配置不一样，
> 调试能跑不代表发布能跑。"
> —— 这是真实工程里非常常见、很多人栽过的坑。

## 7. 第六步：没有 Mac，怎么拿到 iOS 的证据

**这就是整套方案里最关键的一步。** 你不需要买 Mac，GitHub 免费给你一台。

### 7.1 原理（一句话）

GitHub 的 CI 机器里**有 macOS 的型号**，公开仓库免费不限量。
我们在上面装 Flutter、编译 iOS、启动 iOS 模拟器、自动演示 45 秒并录屏，然后把视频给你下载。

**产出物就是一段 iPhone 界面上的真实功能录屏。** 这和你自己买了 Mac 做出来的**没有区别**。

### 7.2 操作步骤

1. **先把代码推上 GitHub**（没做过就先看 [11](11-上传到GitHub.md)）
   —— 仓库建议设为 **public**，公开仓库的 Actions 分钟数免费且不限量。

2. 打开仓库页面，点上方的 **Actions** 标签页。

3. 左边栏找到「**iOS 模拟器构建与录屏**」，点进去。

4. 右边有个 **Run workflow** 按钮，点开 → 绿色的 **Run workflow** 确认。

5. **等 15～25 分钟**（要装 Flutter、编译 iOS、跑模拟器，慢是正常的）。
   页面上的黄点转圈就是在跑。

6. 变成**绿色对勾**后，点进这次运行，往下滚到最底部的 **Artifacts**，
   下载 `ios-simulator-recording`，里面是：
   - `ios-demo.mp4` —— iOS 模拟器上的录屏
   - `ios-screenshot.png` —— 一张截图

### 7.3 跑失败了怎么办

**不需要你会 iOS 开发。** 点进失败的那一步，把红色报错整段复制给 AI，
说"这是 GitHub Actions 跑 iOS 构建的报错，帮我看看"。

> 这个 workflow 是**手动触发**的（`workflow_dispatch`），
> 不会在你每次推代码时自动跑、白烧时间。想跑才跑。

**推之前，先在本地跑一次这个：**

```bash
cd C:\Users\chenj\eclipse-workspace\demo0
node scripts/check-workflows.mjs
```

它专门查一类坑：工作流里**引用了一个不存在的步骤 id、
或者一个没声明的输入框**。这类错在本机怎么跑都是好的，
**要推到 GitHub 才会第一次炸** —— 而那时候一次要等 20 分钟。

它一秒钟出结果，已经接进 `run-tests.bat`（第 1/4 步），所以双击那个批处理就顺带跑了。

> ⚠️ 但它**只查引用对不上**：YAML 缩进、镜像标签（`macos-14` 还在不在）、
> `actions/checkout@v4` 这个版本有没有过期，它都查不出来 —— 那几类只有真跑一次才知道。
> 所以它是"少踩一个坑"，不是"保证能过"。

### 7.4 为什么这个办法是"正当"的，不是投机取巧

面试官关心的是**这个 App 在 iOS 上到底能不能跑**。这个方法回答的正好就是这个问题：

- 它用的是**真的 Xcode**、**真的 iOS 模拟器**、**真的你的代码**
- 编译产物是真的 `.app`，装进真的模拟器，界面是真的渲染出来的
- 全程有**构建日志**留档，做不了假

唯一的区别只是：屏幕在那台云机器上，不在你桌上。

## 8. 第七步：如果面试官要你"当场演示 iOS"

CI 录屏能应付 95% 的场景。万一对方要求**实时操作 iOS**（比如视频面试时让你改个数字看看）：

**去租一小时的云 Mac**（MacinCloud 等，约 ¥25/小时）。
连上去之后操作和你自己的电脑一样，[03](03-跑通App.md) 的流程照做一遍就行。

**不要为了这个去买 Mac。** 一小时几十块钱能解决的问题，不值得花几千块。

## 常见问题

| 问题 | 答案 |
|---|---|
| 我没有安卓手机，只有 iPhone？ | 反过来做：iPhone 连局域网 IP 在 iOS 17+ 上可能被 ATS 拦（见 [03 §4.2](03-跑通App.md)），**更推荐先部署公网 HTTPS 后端**（[06](06-部署后端到公网.md)），iPhone 直接连域名 |
| 我没有手机，只有模拟器行吗？ | 行，功能能测。但**录屏不好看**，而且模拟器连的地址是 `10.0.2.2` 不是局域网 IP，见 [03](03-跑通App.md)。真机效果更好 |
| GitHub Actions 要我付钱吗？ | **公开仓库完全免费、分钟数不限**。GitHub 官方文档原话："GitHub Actions usage is free for self-hosted runners and for public repositories that use standard GitHub-hosted runners"，以及"Public repositories: Minutes remain free"。**所以仓库一定要设为 public。**<br>私有仓库是每月 2000 分钟（Free 档），而按当前单价：**macOS 机器 $0.062/分钟，Linux 才 $0.006/分钟**（约 10 倍）。跑一次 iOS 要 15～25 分钟，**私有仓库跑几次就烧完了**。<br>⚠️ 另外文档里明确写了"Larger runners are always charged for"，我们用标准机器，不受影响 |
| CI 跑一次 25 分钟太久了 | 它跑它的，你干别的。**一天只跑一次就够**，这不是开发循环里的事 |
| 它跑在哪个 macOS 上？我要改吗？ | 工作流钉的是 **`macos-15`**（自带 Xcode 16.4 和 iOS 18.x 模拟器），iOS 模拟器和 `xcrun simctl recordVideo` 在 GitHub 的 macOS 机器上都是现成的，不用装。<br>**别改回 `macos-14`** —— GitHub 从 2026-07-06 起弃用它，**2026-11-02 之后彻底消失**，那天起这个 label 会直接报"不再支持"，而报错内容和工作本身毫无关系，很难往镜像上想。<br>**也别图省事写 `macos-latest`** —— 它现在指向 macos-26（Xcode 26.6），而且会随时间漂移：今天能跑，半年后 GitHub 把 latest 挪到下一版就可能在你不改代码的情况下挂掉。我们在本机验证的是 Flutter 3.47.7，钉死镜像版本是为了让"验证过的东西"和"CI 上跑的东西"是同一个 |
| 我需要学会 iOS 开发吗？ | **完全不需要**。CI 里那些命令是现成的，你只需要会点 "Run workflow" 和下载文件 |
| 面试官问"你没 Mac 怎么写 iOS 的？" | 照实说："代码是一套 Flutter，iOS 工程和安卓工程都在仓库里；我没有 Mac，所以用 GitHub 的 macOS 机器做构建和模拟器验证，产物和录屏都在这里。" —— **诚实的答案比装出来的强，而且这本身就是一种工程能力** |
| 我用 Git Bash 里的 curl 发中文，存进去变成乱码 | **这是我实测踩到的坑，不是后端的问题。** Windows 的 Git Bash 会把命令行里的中文按控制台编码转一遍，中文在 curl 发出**之前**就已经被毁掉了（存进数据库的是 `U+FFFD` 替换字符）。要测接口就用 `cd backend && npm run smoke`（77 条断言，含中文往返），别用 Git Bash 手敲 curl 发中文 |
